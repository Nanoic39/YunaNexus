# 开发过程中的问题与记录

## Q：针对`timestamp`类型的数据库数据，后端实体类该用 `LocalDateTime`还是`java.sql.Timestamp`
选择`LocalDateTime`。
- 第一，`LocalDateTime`是 Java 8 之后推出的新时间 API，线程安全，设计更合理，而 java.sql.Timestamp 线程不安全，属于旧版 API，现在已经不推荐使用。
- 第二，`MyBatis`等持久层框架已经原生支持数据库`timestamp`与`LocalDateTime`之间的自动类型转换，不需要额外配置，使用起来非常方便.
- 第三，在返回给前端时，我可以通过`Jackson`全局配置，将`LocalDateTime`统一序列化为 13 位毫秒时间戳，满足前端展示和交互需求。
- 第四，`LocalDateTime`的 API 更丰富，在时间计算、格式化、业务逻辑处理上都比`Timestamp`更简洁、更易维护。

## Q：为什么要使用LambdaQueryWrapper？
在项目中使用 LambdaQueryWrapper，主要是为了简化 MyBatis-Plus 的单表条件查询，同时解决传统查询方式的痛点
- 第一，它是类型安全的，用 Lambda 引用实体字段，不会出现手写字符串字段名的错误；
- 第二，代码更简洁，链式编程快速拼接查询条件，不用写 SQL；
- 第三，便于维护，字段修改时能快速感知，提升开发和迭代效率。
与普通QueryWrapper相比，QueryWrapper用字符串字段，容易写错且无编译检查；
而LambdaQueryWrapper用方法引用，编译期校验、无魔法值、更安全。

## Q：本系统文件服务数据库设计是如何实现"秒传"功能的？
前端对计算待上传文件的SHA256，后端在file_object表中查询该哈希值，如果命中则直接在在user_file插入一条指向该object_id的记录并将引用计数+1，随后直接返回上传成功的结果，无需实际传输文件流。此外，为了防止哈希碰撞，我还对相同哈希值的文件进行了文件大小与默克尔树证明保证文件完全一致。

## Q：目录层级很深时，如何快速查询某个文件夹下的所有文件？
该设计中已经冗余设计了 folder_path 字段（如 /yuna/2026/photos/）。通过 LIKE '/yuna/2026/%' 可以利用前缀索引快速检索子树，避免了递归查询 DB 的性能黑洞。

## Q：物理删除（彻底删除）的流程是怎样的？
这是一个异步过程：
1. 用户删除逻辑文件，user_file 进入回收站状态。
2. 用户清空回收站，触发 user_file_delete_task。
3. 系统检查该物理对象的 ref_count。若为 0，则标记物理对象为“待清理”。
4. 后台定时任务根据 file_object_replica 真正删除物理文件

## Q：如何处理大文件的断点续传？
1. 记录每个分片的序号、大小、校验值及上传状态。
2. 所有分片上传完成后，再合并生成物理对象记录。

## Q：为什么不能使用Value注解从配置文件中动态读取RSAConstant的属性？
RSAConstant是一个静态类，它的属性都是静态的，不能通过Value注解动态读取。final常量在编译时就确定了，不能在运行时被修改。
如果需要在运行时动态修改RSAConstant的属性，需要在运行时通过反射来实现。

## Q：本项目中为什么要使用Redisson？
Redisson是一个基于Redis的Java客户端库，它提供了Redis的Java API，使开发人员可以更方便地使用Redis，原生支持锁重入，有 Watchdog 机制自动续期，有自带的限流算法。因此替换掉了原本使用的手写Lua注入方法，使用Redisson来实现锁的管理。
