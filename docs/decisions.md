# YunaNexus · 架构决策记录（ADR）

> 本文档记录所有关键技术选型的决策、备选方案与取舍。决策一旦通过，作为后续开发的约束，除非有充分理由否则不轻易推翻。格式参考 ADR（Architecture Decision Record）。

---

## ADR-001 全局内部 ID 采用号段模式

- **状态**：✅ 已采纳
- **背景**：分库后数据库自增 ID 会冲突，需要全局唯一 ID。
- **决策**：采用 Leaf-segment 号段模式（`yunanexus-meta` 统一发号，乐观锁 + 双 Buffer）。
- **备选方案**：
  - Snowflake：纯内存、百万 QPS、时间有序，但依赖时钟需处理回拨、workerId 需协调。
  - 号段为主 + Snowflake 兜底：可靠性最高，但双机制维护成本高，超大规模才值得。
- **理由**：趋势递增利于 B+ 树、无时钟回拨、DB 压力极小，且与已建好的 `id_segment` 表完全契合。
- **代价**：实例重启/优雅停机浪费未用完号段（产生断档，属设计允许）、非严格连续。

## ADR-002 外部 ID 采用加密可逆方案

- **状态**：✅ 已采纳
- **背景**：内部 ID 纯数字易遍历，需对外提供安全的外部 ID。
- **决策**：AES-CTR + HMAC + Base62，密钥版本化；IV 采用随机 IV（详见 ADR-014）。
- **备选方案**：
  - 短码映射（不可逆）：更安全、无密钥，但网关热路径需查 Redis，多一跳 + 强依赖。
  - 明文结构化 ID：实现最简单、可排序（Google/Meta 主流），但可被遍历，需靠鉴权 + 限流防枚举。
- **理由**：网关免查表即可解码出 internalId + 分片，短码防遍历，密钥可版本化轮换。
- **代价**：密钥是单点（泄露即可枚举），密钥管理与分发是核心负担。

## ADR-003 认证采用自建 SSO

- **状态**：✅ 已采纳
- **背景**：所有客户端均为自研，需要统一登录。
- **决策**：自建 SSO（JWT access 30min + refresh 7d + Redis 会话 + 黑名单）。
- **备选方案**：
  - Spring Authorization Server：省协议细节，但绑定 OAuth2 模型、学习曲线陡，与「不用 OAuth2」既定决策冲突。
  - Keycloak：开箱即用，但引入重型独立服务、定制受限、集成成本高。
- **理由**：全可控、轻量、无外部依赖，已设计好的 6 张 auth 表直接复用。
- **代价**：安全细节（刷新/撤销/多设备踢人/CSRF）需自行兜底。

## ADR-004 分库分表采用自研路由

- **状态**：✅ 已采纳
- **背景**：用户中心等数据量大的服务需要分库。
- **决策**：`AbstractRoutingDataSource` + MyBatis 拦截器 + ThreadLocal 精确路由。
- **备选方案**：
  - ShardingSphere-JDBC：成熟、标准化，但依赖重、兼容性踩坑、SQL 受限。
  - 原生多数据源手动切换：太朴素，无迁移/治理能力。
- **理由**：轻量、完全可控、无额外依赖，配合分片号精确路由。
- **代价**：路由/迁移/治理逻辑需自行实现并充分测试。

## ADR-005 服务间调用采用 OpenFeign

- **状态**：✅ 已采纳
- **决策**：Spring Cloud OpenFeign + Nacos 注册发现。
- **备选方案**：
  - Dubbo：高性能、同生态，但强绑定 Dubbo、学习成本高。
  - gRPC：性能最强、跨语言，但 Spring 集成需适配、HTTP 调试不便、本项无跨语言需求。
- **理由**：声明式 HTTP、与 Spring/Nacos 一体、排错直观、社区资料多。
- **代价**：HTTP 性能与序列化体积略逊于 RPC，超大规模（万级实例）不如 RPC。

## ADR-006 分布式事务采用最终一致 + 补偿

- **状态**：✅ 已采纳
- **背景**：注册、审计等跨服务操作需要一致性保证。
- **决策**：本地消息表 + RocketMQ 事务消息 + 幂等 + 补偿 + 对账。
- **备选方案**：
  - Seata AT/TCC：近似本地事务，但全局锁 + 两阶段提交带来性能损耗，对号段/高并发不友好。
  - 混合（默认最终一致 + 强一致 Seata）：兼得但双模型维护成本高。
- **理由**：本中控台强一致场景极少，最终一致可控、不锁库、性能好。
- **代价**：需自行实现幂等/补偿/回查，弱一致性（最终一致）。
- **预留**：若未来出现资金/计费强一致诉求，局部引入 Seata TCC。

## ADR-007 消息队列采用 RocketMQ

- **状态**：✅ 已采纳
- **决策**：RocketMQ（事务消息、延迟消息、Tag 过滤）。
- **备选方案**：
  - Kafka：生态最丰富、流处理强，但 At-least-once 幂等需自行处理、延迟消息弱。
  - RabbitMQ：路由灵活、管理友好，但吞吐最低、延迟/事务消息弱。
- **理由**：事务消息天然契合本地消息表，与 Nacos/Sentinel 同生态。
- **代价**：运维需 NameServer + Broker + Console，生态偏阿里。

## ADR-008 限流熔断采用 Sentinel

- **状态**：✅ 已采纳
- **决策**：Sentinel（QPS/线程数限流、熔断降级、热点参数限流、规则动态下发）。
- **备选方案**：
  - Resilience4j：轻量纯代码库，但无控制台、规则下发需自搭、集群限流弱。
  - 自研 Redis+Lua 限流：轻量，但只限流不熔断。
- **理由**：功能完整、与 Nacos 同生态、支持网关集成。
- **代价**：部分高级功能（集群限流/网关集成）配置复杂。

## ADR-009 网关采用 Spring Cloud Gateway

- **状态**：✅ 已采纳
- **决策**：Spring Cloud Gateway（WebFlux）+ Nacos 动态路由 + Sentinel 限流。
- **备选方案**：
  - APISIX/OpenResty：性能强，但引入非 JVM 栈、认证限流需 Lua 重写。
  - Zuul：已停维护，不采纳。
- **理由**：与所选技术栈同体，动态路由/限流/JWT 一栈搞定，官方推荐。
- **代价**：WebFlux 不能引 common-web（需自己写 Bean），调试链路与 MVC 略不同。

## ADR-010 可观测性采用 SkyWalking + Prometheus/Grafana

- **状态**：✅ 已采纳
- **决策**：Micrometer（指标）+ SkyWalking（链路追踪）+ Prometheus + Grafana（展示）+ 日志采集。
- **备选方案**：
  - Zipkin：轻量，但大规模链路分析弱于 SkyWalking。
  - ELK：日志检索强，但资源占用高、链路追踪非强项。
- **理由**：SkyWalking 对 Java 无侵入、链路追踪强；Prometheus/Grafana 云原生监控标配。
- **代价**：多套组件运维。

## ADR-011 配置与密钥采用 Nacos + Secret 分层

- **状态**：✅ 已采纳
- **决策**：Nacos Config 管普通配置；敏感项（AES/HMAC 密钥、DB 密码）入 K8s Secret / 环境变量。
- **备选方案**：
  - Spring Cloud Config：Git 集成好，但需自建 Server、热更新弱。
  - 纯 K8s ConfigMap/Secret：最简，但无热更新、无集中管理。
- **理由**：Nacos 与已选技术同生态、支持热更新；敏感配置分层保护。
- **原则**：敏感配置**永不**明文入 Nacos / 代码仓库。

## ADR-013 分片编号为独立字段（废弃 InternalIdRouter）

- **状态**：✅ 已采纳
- **背景**：内部 ID 采用号段模式后，分片信息无法内嵌于内部 ID。
- **决策**：分片编号为独立字段，存 `auth_user.shard_index`，作为 `encode(internalId, shardIndex)` 独立参数。
- **废弃**：`InternalIdRouter`（从内部 ID 位运算取分片）删除。
- **理由**：号段模式按 `biz_tag` 发号，无分片维度；分片决策由用户中心在注册时完成。
- **影响**：网关解码外部 ID 得到分片，运行时无需从 ID 反推。

## ADR-014 外部 ID 采用随机 IV（非确定性输出 + 落库）

- **状态**：✅ 已采纳
- **背景**：固定 IV 导致 many-time-pad 泄露（可反推 ID 相对顺序）；按 internalId 派生 IV 则解密死循环。
- **决策**：每次 encode 生成随机 IV，编码进 payload，随密文一起 HMAC 保护。**encode 非确定性**；外部 ID 的稳定性通过**「注册时 encode 一次 + 落库」**保证（`auth_user.external_id` 列 UNIQUE，落库后只读不重算）。
- **备选方案**：
  - 固定 IV：确定性但 many-time-pad 泄露。
  - 按 internalId 派生 IV：确定性但解密死循环。
  - 按 shardIndex 派生 IV：同分片内仍 many-time-pad 泄露，仅比全局固定略好。
- **理由**：彻底消除 many-time-pad 泄露与解密死循环；SSO 稳定性由落库保证，不依赖 encode 确定性；解码自包含（IV 在 payload 内），抗密钥轮换。
- **代价**：外部 ID 变长（固定 29 位）；`auth_user` 增加 `external_id` 列。

## ADR-015 JWT RS256 签名密钥版本化轮换（kid）

- **状态**：✅ 已采纳
- **背景**：JWT 签名需支持平滑轮换与泄露应急；HMAC 共享密钥在多服务验签场景下分发面过大。
- **决策**：
  - JWT 采用 **RS256** 签名，`kid` 放在 JWT 头，`alg` 固定为 `RS256`。
  - 认证中心配置属性前缀为 `yunanexus.auth.jwt`、`active-kid` 指向当前签发密钥；`keys` 列表中 active 项必须同时包含公钥和私钥，历史项只保留公钥用于验签。
  - 新签发使用 `active-kid` 对应私钥；验证按 `kid` 选择对应公钥。
  - 普通轮换周期 90 天：新增新 `kid` 为 active，旧 `kid` 降为历史公钥，保留至少 `最长 refresh token 寿命 + 时钟余量`，待所有旧 token 过期后再移除。
  - 泄露应急：泄露的 `kid` 立即从 keys 中移除/撤销，不无限保留泄露密钥；已签发 token 全部失效，用户需重新登录。
  - 缺失或无效的 active 公私钥导致启动拒绝（failfast），**不允许 HMAC 降级**。
- **理由**：与外部 ID 密钥版本化同思路，实现平滑轮换；RS256 支持公钥分发给网关/下游验签，私钥不出认证中心。
- **代价**：维护 RSA 密钥对列表与 `kid` 解析逻辑；RSA 签名/验签开销略高于 HMAC。

## ADR-016 分布式锁采用 Redisson

- **状态**：✅ 已采纳
- **背景**：注册等场景需防止并发重复创建（唯一键竞争）。
- **决策**：Redisson 分布式锁，锁超时 30 秒 + watchdog 续期；获取失败立即返回「注册处理中，请稍后重试」；进程崩溃锁自动过期。
- **备选方案**：手动 Redis setnx + expire（需自行处理续期与死锁）。
- **理由**：Redisson 内置 watchdog 与可重入锁，成熟可靠。
- **代价**：引入 Redisson 依赖。

## ADR-018 安全防护（CSRF/CORS/CSP + 数据脱敏）

- **状态**：✅ 已采纳
- **背景**：SSO 基于 Cookie + JWT，需防跨站攻击与敏感信息泄露。
- **决策**：CSRF（`SameSite=Lax/Strict` + 关键操作 CSRF Token）；CORS（白名单，禁 `*`）；CSP（登录页）；数据脱敏（日志框架层 + 接口响应层）。
- **理由**：生产级 Web 安全基线。
- **代价**：各服务需统一接入安全中间件。

## ADR-019 健康检查与优雅停机

- **状态**：✅ 已采纳
- **背景**：K8s 滚动更新需就绪/存活探针；停机需等待在途请求完成。
- **决策**：readiness（启动完成 + 依赖中间件连通）、liveness（进程存活，不查依赖避免雪崩）、`server.shutdown=graceful`。
- **说明**：优雅停机时未用完的号段直接浪费（ADR-001 允许），无需回写 DB。
- **理由**：保证滚动更新不中断在途请求。
- **代价**：需正确配置探针，避免误判。

## ADR-022 用户行为采集采用自研 SDK

- **状态**：✅ 已采纳
- **背景**：需在几乎无侵入的前提下采集用户行为，支撑画像与产品优化。
- **决策**：自研轻量 JS SDK（自动采集 + `data-track` 声明式标记 + 手动调用兜底），数据自持。
- **备选方案**：
  - 第三方 SaaS（神策/GrowingIO/友盟）：开箱即用、分析平台全，但数据出境/个保法合规风险、按量收费、数据不自持、与自建认证打通需额外集成。
  - 自研核心 + 预留扩展：兼顾自持与演进，但当前直接自研即可。
- **理由**：数据自持、完全可控合规、无出境、与自家网关/认证天然打通。
- **代价**：需自建采集端点与分析能力，功能不如商业产品全。

## ADR-023 行为数据存储采用 ClickHouse

- **状态**：✅ 已采纳
- **背景**：行为明细海量（每次点击一条），需高性能分析引擎。
- **决策**：ClickHouse（列式，漏斗/留存/聚合秒回，百亿级）。
- **备选方案**：
  - Elasticsearch：灵活、全文检索强，但漏斗/留存等多维聚合弱、写入与存储成本高。
  - MySQL 分表：复用现有栈、无新引擎，但聚合性能迅速成瓶颈，仅适合小规模早期。
- **理由**：列式引擎专为行为分析设计，实时+离线均可，压缩率高，大厂标配。
- **代价**：引入新存储引擎需独立运维。

## ADR-024 画像分析采用准实时 + 离线分层

- **状态**：✅ 已采纳
- **背景**：不同场景对实时性要求不同（实时推荐 vs 深度分群）。
- **决策**：准实时（秒~分钟，Redis 实时画像特征）+ 离线（T+1，ClickHouse 分群/漏斗/留存）。
- **备选方案**：
  - 仅离线 T+1：简单低成本，但无法支撑实时推荐/画像/即时反馈。
  - 全实时流处理（Flink）：最及时，但引入流计算引擎，复杂度与成本最高，当前过度设计。
- **理由**：生产级标准分层，按需逐步增强。
- **预留**：实时要求提升到秒级强一致时，引入 Flink。

## ADR-025 号段采用动态步长（消耗速率自适应）

- **状态**：✅ 已采纳
- **背景**：固定步长无法适应业务增长：步长过小导致取号频繁打库，过大导致实例重启浪费号段（ADR-001 的断档代价被放大）。
- **决策**：每次号段耗尽后，按上一号段的消耗速率反推下一号段步长：目标步长 = 速率 × 期望缓冲时长，与上一段步长加权平滑（系数 0.5），最终钳制在 `[minStep, maxStep]`。步长随乐观锁领取一并持久化到 `id_segment.step`。
- **备选方案**：
  - 固定步长：实现最简，但无法适应负载变化。
  - 每次领取实时计算但不持久化：计算不稳定（重启/多实例各算各的），且无法回看历史。
- **理由**：号段步长自适应，既控制打库频率，又把「重启浪费」控制在可接受范围；持久化保证多实例/重启后步长平滑延续。
- **代价**：`updateMaxId` 需在推进 `max_id` 的同时更新 `step`（一条 SQL 完成，无额外开销）。

## ADR-026 号段服务预加载失败降级策略

- **状态**：✅ 已采纳
- **背景**：异步预加载失败若只打印日志，会持续空转打库，且当前号段耗尽后无预备号段，用户无感知。
- **决策**：连续异步预加载失败达到阈值（默认 5 次）后进入「降级」状态——停止异步打库，转由同步兜底加载；同步加载成功即自动退出降级。降级状态通过 Micrometer 指标与 `SegmentHealthIndicator` 暴露，供 readiness 探针摘流。
- **理由**：明确失败语义（不静默失败），降级后取号路径仍可用（同步兜底），并在 DB 恢复后自动愈合；探针联动支持实例级摘流，避免把坏实例流量放大。
- **代价**：引入降级状态机与指标，逻辑略增。

## ADR-027 认证采用 RS256 + 服务端会话绑定（JWT 仅外部身份）

- **状态**：✅ 已采纳
- **背景**：早期设计为 HMAC（对称密钥）JWT，密钥泄露即全网可伪造；且若 JWT 自包含会话状态，用户信息变更/踢人无法即时生效。
- **决策**：
  - JWT 使用 **RS256**（RSA 非对称），`kid` 置于 JWT 头；签发用 `active-kid` 私钥，验证按 `kid` 选公钥。启动强制校验 RSA ≥ 2048、active 公私钥匹配、kid 唯一；**禁止 HMAC / none / RS512 降级**（`keyLocator` 硬编码 RS256 白名单）。
  - JWT `claims` 只放外部身份：`sub`（外部 ID）、`typ`、`client`、`sid`、`jti`、`iss`、`iat`、`exp`；**不含 `uid`/`userId`/用户名**。
  - **验签通过 ≠ 会话有效**：内部身份与会话状态绑定在服务端 Redis（会话 + 撤销索引 + 账号纪元），每次受保护请求复验会话存在、access jti 匹配、epoch 匹配、客户端/平台授权。
- **备选方案**：
  - HMAC 对称签名：实现简单，但密钥泄露即可伪造任意令牌，且无法安全地把验证能力分发到网关（需下发签名密钥）。
  - JWT 自包含会话/权限：无状态、少一跳，但踢人/改权/禁用无法即时生效，需等令牌过期。
- **理由**：RS256 让网关/其他服务仅凭公钥验签、无法伪造；服务端会话绑定保证撤销即时生效（单点登出、踢人、禁用、全局纪元撤销）。
- **代价**：每次请求多一次 Redis 会话查询；密钥对（RSA3072）运维与轮换成本。

## ADR-028 注册采用本地消息表（outbox）+ 幂等回查补偿

- **状态**：✅ 已采纳
- **背景**：注册跨 meta（取号）/ auth（写 auth_user）/ user（写 sys_user）三服务，跨服务强一致不可得，中途失败会产生不一致。
- **决策**：
  - 认证中心在**同一本地事务**内写入 `auth_user` 与注册 outbox 记录（`auth_register_outbox`，`user_id` 唯一），保证「注册成功 ⇔ 有待同步记录」。
  - 后台补偿任务（`@ConditionalOnProperty` 开关，用户中心就绪后开启）扫描 PENDING 记录：先幂等回查用户中心是否已存在，再创建；失败按指数退避重试，超上限置 FAILED 并告警。
  - 用户中心提供幂等接口（以 `userId` 为幂等键），使 outbox 重试安全。
  - 分片决策抽象为可插拔 `ShardAllocator`：阶段 5 前由认证中心取模决策（`ModShardAllocator`），阶段 5 后可替换为用户中心决策。
- **备选方案**：
  - 同步 Feign 调用 + 失败即回滚注册：跨服务无分布式事务，回滚不可靠（用户中心可能已写入）。
  - Seata TCC：强一致，但全局锁 + 两阶段提交对注册吞吐不友好，与本项目「强一致场景极少」定位不符（见 ADR-006）。
- **理由**：最终一致、不锁库、注册路径快；outbox 随注册落库不丢失，补偿可重入（幂等）。
- **代价**：需实现 outbox 表、补偿任务、幂等回查；引入最终一致延迟窗口（用户资料稍后可见）。

## ADR-029 文件存储采用抽象接口 + 本地实现（云存储预留）

- **状态**：✅ 已采纳
- **背景**：文件中心需同时支持本地联调（无云存储账号）与生产部署（对象存储）。若直接绑定某云厂商 SDK，本地开发强依赖外部服务，后续切换厂商成本高。
- **决策**：定义 `FileStorage` 抽象接口（保存 / 读取 / 删除 / 路径生成），阶段 7 提供 `LocalFileStorage`（本地文件系统）实现；MinIO / OSS 作为后续实现按需接入，通过配置切换，业务代码不改。`file_meta.storage_type` 记录实际后端（1-本地 / 2-MinIO / 3-OSS）。
- **备选方案**：
  - 直接集成 MinIO / OSS SDK：上手快，但本地联调依赖外部服务，换厂商需改业务代码。
  - 仅用 Spring `Resource` 抽象：偏「读取」，缺少写入 / 删除 / 路径策略，仍需自行封装。
- **理由**：接口隔离存储细节，本地零外部依赖跑通，生产可平滑切换云存储；`storage_type` 落库支持多后端并存与后续迁移。
- **代价**：多一层抽象与一次配置分发。
