# YunaNexus · 分库扩容 SOP

> 用户中心从 N 库扩到 M 库的标准操作流程（阶段 9 演练，阶段 5 落地基础）。目标：扩容过程用户无感知，外部 ID 不变。

---

## 一、前置约束（回顾）

- 外部 ID 编码了**逻辑分片编号**（0~15），不编码物理库。
- 配置中心维护 `逻辑分片 → 物理库` 映射，扩容只改映射，外部 ID 不变。
- 内部 ID 由号段中心统一发号，**不含分片信息**，天然支持任意分片迁移。

### 逻辑分片总数的硬上限

- 分片编号在外部 ID 明文中占 **4 bit**，取值 **0~15，即最多 16 个逻辑分片**，这是**硬上限**。
- 若未来业务超过 16 逻辑分片，需**扩大分片位宽**（如 4 bit → 8 bit），这会改变外部 ID 的编码格式与长度，**导致全部历史外部 ID 失效**，属于**大版本变更**，需整体迁移，不视为普通扩容。
- 因此当前设计容量为 **16 分片**，扩容在 16 内进行；跨过 16 需走大版本改造（另行立项）。

---

## 二、扩容目标示例

| 项 | 扩容前 | 扩容后 |
| :--- | :--- | :--- |
| 逻辑分片数 | 0~3（4 分片） | 0~7（8 分片） |
| 物理库 | db_user_0 ~ db_user_3 | db_user_0 ~ db_user_7 |

---

## 三、操作步骤

### 步骤 1：准备新库

1. 创建新物理库 `db_user_4` ~ `db_user_7`，执行 `sys_user` 建表脚本。
2. 配置动态数据源，注册新 DataSource（服务重启后生效，或热加载）。

### 步骤 2：迁移存量数据

1. 按 `shard_index` 筛选待迁移分片的数据。
2. 用迁移工具（如 DataX / 自研脚本）全量同步到新库。
3. 开启增量同步（binlog），追平迁移期间的写入。

### 步骤 3：更新映射

1. 配置中心新增 `逻辑分片 4 → db_user_4` 等映射。
2. 逐步放量：先切少量流量观察，再全量切换。

### 步骤 4：校验与回滚

1. 抽样比对迁移前后数据一致性（行数、关键字段 hash）。
2. 异常时回滚映射到旧库，旧库数据仍保留。

---

## 四、数据校验方式

| 维度 | 方法 |
| :--- | :--- |
| 行数 | 源库 vs 目标库 count 比对 |
| 字段一致性 | 抽样行 hash 比对 |
| 业务校验 | 关键用户资料字段 spot-check |

---

## 五、回滚方案

- **映射回滚**：逻辑分片映射指回旧库（秒级生效）。
- **数据回滚**：迁移失败时目标库数据丢弃，重走迁移流程。
- 旧库数据**至少保留一个迁移周期**，确认无误后再清理。

---

## 六、演练要求（阶段 9）

- 在预发环境完整演练一次扩容 + 回滚。
- 记录各步骤耗时，输出优化点。
- 演练通过后方可在生产执行。
