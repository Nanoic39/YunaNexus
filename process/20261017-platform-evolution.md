# 积分、签到与多应用权限改造

## 需求与边界

1. 全平台共用用户积分账户；其他三方只能扣减，不能通过充值、退款或负数扣减增加余额。
2. 签到按 Asia/Shanghai 自然日计算，每日一次；连续签到有额外奖励，断签重新计算。
3. 应用分类：OFFICIAL_NATIVE（官方原生）、OFFICIAL_THIRD_PARTY（官方三方）、THIRD_PARTY（其他三方）。分类由超级管理员审核设置，申请者不能自称官方。
4. 官方应用可使用账号密码登录并建立现有 SSO 会话；所有已启用且获用户授权的应用可使用授权码和 refresh_token。保留刷新轮换、账号 epoch 与平台授权校验。
5. 应用权限目录、角色和成员授权使用应用 ID 作为隔离键；不复用平台管理员角色，不向三方返回平台权限全集。

## 架构决策

- 统一积分账本放在认证库，由认证服务提供应用身份校验及事务边界，避免跨服务写入或分片账户出现多份余额。积分是 BIGINT 整数，余额不允许为负。
- 每笔变更包含应用、用户、业务幂等键、方向、数量、余额、创建时间。账户行锁串行化并发；同一幂等键重试返回原记录，参数不同则拒绝。
- 每日签到记录与积分入账同一事务，日期来自服务端时钟，浏览器时间不参与判定。基础奖励及连签奖励由服务端配置。
- 第三方扣款必须同时拥有用户授权范围及应用服务端凭证；不能仅凭客户端上传的 userId、appId 或分类操作他人积分。第三方退款仍属于增加，禁止直接调用，应走平台审核补偿流程。
- 应用权限代码仅在当前应用内有意义。平台维护角色与应用维护角色完全分离；查询和写入都使用服务端认证得到的 clientCode 限定范围。
- 接入方可以建立自己的角色和权限目录，通过平台批量检查接口鉴权；平台只负责身份、授权关系和判定，不替代接入方自身业务资源归属检查。
- 时间输出统一 UTC 带 Z，签到展示日期单独返回业务时区日期。

## 验收要求

重复签到不重复入账；跨日与断签正确；并发扣款无负余额；幂等冲突拒绝；三方增加积分拒绝；停用应用、撤销授权与缺失 scope 拒绝；应用 A 无法读写应用 B 的角色和权限；普通管理员不能把自己的应用升级成官方；现有门户登录与 SSO 不回归。

### 实测问题记录

真实 MySQL 并发测试发现 INSERT IGNORE 的共享锁升级导致死锁，CI 阻止发布。改用 no-op upsert 先获得账户排他锁，保留原并发用例重新验证。公开资源撤销后的错误响应原为 HTTP 200，已补充真实 404 回归用例，待修复部署后再次验收。

线上回归发现登录边缘限流默认返回503，现保持强度不变改为429；积分流水在新 MySQL 驱动下返回 LocalDateTime 而非 Timestamp，补全两种 JDBC 类型的 UTC 输出，并增加真实数据库时间契约断言。官方密码登录、SSO、刷新、积分限制及跨应用角色隔离已在此前步骤验证通过，修复后仍完整重跑。

最终结果：后端659项回归、前端61项测试及双方CI通过；生产匿名文件、积分、签到、官方密码与SSO、刷新、应用RBAC隔离、即时撤销和清理全部通过。具体版本及边界见 [验收记录](20261017-verification.md)。
